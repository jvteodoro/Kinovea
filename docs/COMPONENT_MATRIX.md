The solution contains 20 project entries (19 classic C# projects and one C++/CLI `.vcxproj`); the two solution folders are not projects. Every listed solution path exists with its recorded case. ## Dependency-aware order and test prerequisites

1. **Timecode logic only**: `Kinovea.Services/TimeHelper.cs` and its `TimecodeFormat`, `TimecodeType`, and timestamp delegate contracts. A package-free source-isolated harness now exists at `tests/Timecode.Characterization`; it links the original source files and passes its documented Linux assertions. Windows legacy comparison remains unavailable, so parity is still `UNVERIFIED`.
2. **Geometry arithmetic and projective mapping**: `Vector3` + `Matrix3x3` and `ProjectiveMapper` in ScreenManager. Source-isolated `net10.0` harnesses pass on Linux; see [arithmetic evidence](evidence/2026-10-11-geometry-characterization.md) and [mapping evidence](evidence/2026-10-11-projective-mapper-characterization.md). ProjectiveMapper's Linux harness uses a narrow test substitute for the `QuadrilateralF` vertex/indexer contract and a no-op logger; it does not exercise `QuadrilateralF.Contains` or calibration callers. Windows legacy comparison remains unavailable, so parity is `UNVERIFIED`. Preserve upstream AForge attribution on the arithmetic files and capture current mapping quirks before changing them.
3. **Video format adapters**: Windows GDI+ Bitmap conversion now has a separately tested adapter boundary; it has not replaced or integrated with the reader. The adapter output was compared with pixel captures produced by the real legacy reader in Windows CI. Continue with a reader/frame integration design only after reviewing its format and lifetime limits. GIF, SVG, and Linux image decoding remain unimplemented and unverified. Use tiny synthetic/licensed fixtures; compare dimensions, decoded pixels/channel order, alpha, orientation, timestamps and corrupt input at their actual boundaries.
4. **Pipeline and camera contracts**: characterize ring-buffer lifecycle and concurrency before modernizing Pipeline; then characterize Camera contracts and FrameGenerator as a deterministic producer. Validate drops, ordering, byte contents, frame timing and teardown; use real camera integrations only where devices and vendor runtimes exist.
5. **FFmpeg boundary and ScreenManager integrations**: first create a separately documented native interop design; preserve probe/decode/seek/timebase/color/buffering semantics through golden fixtures before considering backend changes. ScreenManager remains downstream of portable contracts and format behavior.
6. **Desktop shell, capture adapters, updater and packaging**: last, with real UI, device, update and workflow tests on both OSes. Compile success alone cannot validate these boundaries.
